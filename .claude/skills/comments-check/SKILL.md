# 注释体检工作手册（comments-check）

给代码注释做体检：默认**只检查、出报告，不改代码**；用户明确要求修复时才改，且只改注释、不动代码逻辑。

## 三条检查标准

### 1. 注释是否缺失（覆盖率）

- 每个函数/方法/类都应有说明注释：本项目风格是中文 docstring 或函数上方 `#` 注释，说清「干什么、入参出参、什么时候用」。
- 每段重要核心代码应有解释：复杂算法、业务规则、易错点、魔法数字、有意为之的取舍与坑。
- 密度目标：**注释约占 30%**（约 10 行代码配 3 行注释）。
  - 统计口径：注释行 = `#` 开头行 + docstring 行 + 行内注释；分母 = 注释行 + 代码行（空行、纯 import 行不计）。
  - 健康区间 20%~40%；低于 15% 且文件有实质逻辑 → 报「注释缺失」。
  - 30% 是整体目标，不是每 10 行机械凑 3 行；凑数的废话注释不算数。
- 不检查：测试文件、生成代码、第三方依赖、纯常量/配置清单（没有逻辑可注释）。

### 2. 注释与代码是否匹配

逐条核对「注释说的」和「代码做的」：

- 注释描述与代码相反或不符：参数顺序、默认值、返回结构、分支条件、单位说错。
- 过时注释：代码已改、注释没改（提到的字段/函数/阈值已不存在或数值对不上）。
- 复制粘贴错位（张冠李戴）。
- 这类一律 🔴 严重：错误注释比没注释更害人。

### 3. 是否符合小白视角

假设读者是没接触过本模块的新人：

- 专业术语首次出现要解释（如 embedding、向量召回是什么、为什么用）；缩写首次出现写全称（如 SSE = Server-Sent Events）。
- 讲「为什么这样写」（业务原因、坑、权衡），不只复述「是什么」。
- 不写废话注释（`i += 1  # i 加 1` 这种只重复代码本身的）。
- 中文优先，与本项目既有注释风格保持一致。

## 执行流程

1. 确认范围：用户指定文件/目录就查指定的；没指定就查最近改动或当前讨论涉及的代码；拿不准就问。
2. 逐文件读代码（Read），按三条标准收集问题，每条标 `文件:行号`。
3. 每个文件粗略统计注释密度（不必逐行精算，估到百分位即可）。
4. 按下方模板出报告。用户要求修复时，改完重查一遍，报告前后变化。

## 报告模板（大白话）

```markdown
📝 注释体检报告
- 检查范围：N 个文件
- 注释密度：文件A X% / 文件B Y% …（目标约 30%）
- 结果：✅ 合格 / ⚠️ 发现 N 处问题

🔴 严重 · 注释与代码不符（N 处）：
- 文件:行号 — 注释说 X、代码实际做 Y → 建议改法（附可直接粘贴的注释草稿）

🟡 缺失 · 该有注释没有（N 处）：
- 文件:行号 — 缺在哪（哪个函数/哪段逻辑）→ 建议补的注释草稿

🟢 不够小白 · 难懂/术语/废话（N 处）：
- 文件:行号 — 问题 → 建议改法

结论：<一段话总结，先改什么最划算>
```

## 修复模式

用户说「顺便修」「帮我改」时：

- 只改注释（docstring、`#` 注释），**不碰任何代码逻辑**。
- 按报告里的草稿改，改完整体重查一遍，汇报修改前后对比。
- 解释业务规则这类需要用户背景的注释，标出来问用户，不瞎编。

## 注意事项

- 注释好坏是主观判断，标准是「三个月后的自己/刚接手的新人能否看懂」，不是字数多少。
- 密度不达标 ≠ 一定要加注释：函数短小自解释时，不加比加废话强，在报告里说明判断即可。
- 报告一律大白话中文，问题要落到 `文件:行号`，建议要能直接粘贴。
